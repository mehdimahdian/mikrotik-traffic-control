# Languages and translations

Supported: **English** (primary, the source text), **فارسی** (fa), **العربية** (ar), **Русский** (ru), **中文** (zh). The language switcher is in the header; the choice is remembered in the browser and on the server, and defaults to the browser language on first run. The printable report and guest-portal pages have their own language choice (they default to the dashboard language).

## How it works

* The English text in the HTML/JS **is the key**. A dictionary per language, `src/public/i18n/<lang>.json`, maps `"English text"` to the translation. No key in the code needs renaming.
* `src/public/i18n.js` translates the page text, `placeholder`, `title`, `alt` and `aria-label`, and keeps doing so for content the dashboard renders later (a `MutationObserver`). Switching language never reloads the page.
* Sentences with values use placeholders: the key `"{0} of {1} devices"` matches "95 of 220 devices" and is translated with the captured values: `"{0} از {1} دستگاه"`. In code, `__('Saved {n} files', { n: 3 })` does the same.
* Missing keys fall back to English, so a partial translation always works.
* Weekday and date names come from the browser (`Intl`), so they follow the language automatically.

## Right-to-left (Persian, Arabic)

Setting `<html dir="rtl">` mirrors the layout (flex/grid and logical CSS properties). The rules in the `:root[dir=rtl]` block of `index.html` keep **numbers, units, IP/MAC addresses and rates left-to-right and readable** ("93.1 Mbps" stays "93.1 Mbps"), resolve mixed text by its first letter (`unicode-bidi: plaintext`), keep charts and tooltips LTR, and mirror the slide-in panel. Persian/Arabic text uses the bundled **Vazirmatn** font. The week starts on Saturday for fa/ar and Monday otherwise.

To add another RTL language, add it to `LANGS` in `i18n.js` with `rtl: true`.

## Improving or adding a translation

1. Edit `src/public/i18n/<lang>.json` directly (plain JSON), or
2. `node tools/i18n-check.js <lang>` lists the English strings that have no translation yet; add them to the JSON.

New language `xx`:

1. Create `src/public/i18n/xx.json` (`{}` is fine to start).
2. Add `xx: { name, rtl, weekStart, locale }` to `LANGS` in `src/public/i18n.js`.
3. Add `xx` to `LANGS` in `src/manager.js` and an `<option>` to the `#lang` select (and the report/hotspot language lists if wanted).
4. For guest-portal pages add a block to `T` in `src/hotspot.js`.

## The numbered sources (`i18n-src/`)

The first dictionaries were written as numbered lines (`N|translation`) aligned with `i18n-src/keys.txt`, and compiled by `node tools/build-i18n.js` (it prints coverage). After that, the JSON files are the thing to edit; re-running the build overwrites them, so only use it if you keep working in the numbered files.

## Coverage

`node tools/i18n-check.js` prints how many strings of the current dashboard are translated per language (about three quarters of the extracted strings; most of the rest are code fragments the extractor cannot tell from text, plus a few long help paragraphs, which stay English until translated). Messages that come from the server (error texts returned by the API) are English.

`npm test` includes translation sanity tests: valid JSON, string values, **placeholders identical to the English key**, and every language registered in `i18n.js` and `manager.js`.

## Guidelines

Keep technical terms people know in their Latin form (SSH, MAC, DHCP, VPN, Mbps, IP). Keep placeholders (`{0}`, `{n}`) exactly. Use Western digits (0-9). Keep the translation about as short as the English: many labels sit in narrow table headers and buttons.
